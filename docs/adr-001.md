# ADR-001: Architectural Decision Record

## Título: Adoção do PostgreSQL como Banco de Dados Relacional Principal

* **Status:** Em Elaboração
* **Contexto:** Projeto de Oficina Mecânica
* **Tecnologias:** Spring Boot, Kotlin, Monolito, Onion Architecture, Spring Data JPA (Hibernate), Flyway
* **Data:** 4 de Junho de 2026

---

## 1. Contexto e Problema

Estamos desenvolvendo o sistema central de uma oficina mecânica utilizando uma arquitetura monolítica baseada em **Onion Architecture** com **Spring Boot** e **Kotlin**. O domínio possui alta complexidade relacional (Clientes, Veículos, Agendamentos, Ordens de Serviço, Itens de Estoque e Faturamento) e exige consistência transacional estrita (ACID).

Precisamos definir o ecossistema de armazenamento de dados e a estratégia de evolução do esquema de forma que:

1. Simplifique o desenvolvimento produtivo da equipe sem violar o isolamento das camadas da Onion Architecture.
2. Garanta a rastreabilidade e versionamento da base de dados desde o dia zero.
3. Alinhe-se a restrições orçamentárias comuns a projetos de software comerciais ou de médio porte, evitando o aprisionamento tecnológico (*vendor lock-in*).

---

## 2. Direcionadores de Decisão (Drivers)

* **Produtividade e Mapeamento Objeto-Relacional (ORM):** Aproveitar a maturidade do ecossistema Spring (Spring Data JPA / Hibernate) para acelerar a escrita e leitura de dados.
* **Evolução Segura do Schema (Database Migrations):** Garantir que alterações no banco sejam versionadas e integradas ao ciclo de vida da aplicação.
* **Custo e Licenciamento (Free & Open Source):** Minimizar custos operacionais de licenciamento, garantindo escalabilidade financeira à medida que o negócio cresce.
* **Consistência e Integridade:** Suporte nativo a transações complexas para evitar falhas críticas de negócio (ex: duplicidade de OS ou faturamento inconsistente).
---
## 3. Alternativas Consideradas

* **Alternativa 1: MySQL / MariaDB**
* *Prós:* Excelente performance de leitura, amplamente conhecido.
* *Contras:* Menos recursos avançados de concorrência e tipos de dados complexos (como JSONB nativo de alta performance) em comparação ao PostgreSQL.


* **Alternativa 2: MongoDB (NoSQL Document)**
* *Prós:* Esquema flexível, escala horizontalmente com facilidade.
* *Contras:* A natureza intrinsecamente relacional e transacional do negócio (Cliente $\rightarrow$ Veículo $\rightarrow$ Ordem de Serviço $\rightarrow$ Itens/Serviços) exige integridade referencial que o NoSQL não prioriza por padrão.


* **Alternativa 3: PostgreSQL**
* *Prós:* Padrão ouro para bancos relacionais de código aberto, suporte excepcional a concorrência (MVCC), conformidade estrita com ACID e recursos avançados (JSONB, enums, CTEs).

---

## 4. Detalhamento dos Novos Critérios

### 4.1. Sinergia com ORM (Spring Data JPA / Hibernate)

A escolha por um banco de dados relacional se justifica fortemente pela robustez das ferramentas de ORM do ecossistema Java/Kotlin.

* O **Spring Data JPA** abstrai a complexidade do acesso a dados, permitindo que a camada de *Infrastructure* (da nossa Onion Architecture) implemente as interfaces de repositório definidas no *Core* (Domain/Application) de forma extremamente limpa.
* O dialeto do Hibernate para PostgreSQL é um dos mais maduros do mercado. Ele mapeia perfeitamente entidades ricas do Kotlin (incluindo *Data Classes*, tipos de data modernos e enums) para tabelas e relacionamentos, otimizando consultas através de recursos como carregamento preguiçoso (*lazy loading*) e cache de primeiro nível.

### 4.2. Gerenciamento de Mudanças com Flyway

Para evitar o caos de scripts manuais executados diretamente em produção, o **Flyway** foi integrado ao ciclo de inicialização do Spring Boot.

* **Versionamento como Código:** Cada alteração no banco (criação de tabelas de OS, adição de colunas em estoque) é escrita em scripts SQL puros (`V1__initial.sql`, `V2__add_index.sql`) e armazenada no repositório Git junto com o código Kotlin.
* **Automação no Monolito:** Sendo uma arquitetura monolítica, o próprio container da aplicação executa as migrações pendentes durante o *startup*, garantindo que o banco de dados esteja sempre sincronizado com a versão do software implantada.

### 4.3. Licenciamento Livre e Modelo Open Source

O PostgreSQL é distribuído sob a **PostgreSQL License** (uma licença liberal de código aberto, semelhante à MIT/BSD).

* **Custo Zero de Licença:** Não há custos ocultos por volume de dados, número de conexões ou núcleos de CPU (diferente de soluções proprietárias como Oracle ou SQL Server). Isso reduz drasticamente o custo total de propriedade (TCO) para a oficina mecânica.
* **Independência de Provedor (*No Lock-in*):** Por ser amplamente adotado e de código aberto, o projeto pode ser executado localmente em ambientes de desenvolvimento (via Docker), em servidores físicos (*on-premise*) na própria oficina, ou migrado facilmente para qualquer nuvem (AWS RDS, GCP Cloud SQL, Azure Cosmos for Postgres) sem necessidade de reescrever uma única linha de código.

---

## 5. Decisão

Confirmamos a adoção do **PostgreSQL** em conjunto com **Spring Data JPA** (para mapeamento e abstração de infraestrutura) e **Flyway** (para governança e migração de dados).

---

## 6. Consequências

### Positivas:

* **Camadas Isoladas:** Os Repositories do Spring Data JPA ficam confinados na camada externa de Infraestrutura, convertendo as tabelas do Postgres em Entidades de Domínio limpas antes de expô-las ao núcleo da aplicação.
* **Rastreabilidade Máxima:** O histórico do Flyway permite auditoria completa de como o banco evoluiu, facilitando auditorias de infraestrutura ou Rollbacks controlados.
* **Eficiência Orçamentária:** O orçamento do projeto pode ser focado em desenvolvimento e infraestrutura de computação, com custo zero para o software de banco de dados.

### Negativas / Desafios:

* **Cuidado com a Performance do ORM:** O uso inadequado do JPA pode causar o problema de consultas $N+1$ em relacionamentos densos (ex: puxar uma OS e fazer uma query extra para cada item de peça). A equipe de desenvolvimento deve ser vigilante no uso de `JOIN FETCH` ou DTOs customizados em Kotlin.
* **Imutabilidade do Kotlin vs. Mutabilidade do Hibernate:** O Hibernate espera entidades mutáveis (com propriedades `var`), enquanto o design idiomático do Kotlin favorece imutabilidade (`val`). Será necessário adotar plugins como o `kotlin-jpa` (que cria construtores sem argumentos em tempo de compilação) para harmonizar essa convivência.
